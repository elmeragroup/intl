---
"@elmeragroup/intl-tools": minor
---

Extraction and the `elmera-intl/extractable` lint rule fail a bare `t(…)` call whose `t` is rooted in an app import, in every file, including files that do not import `@elmeragroup/intl`. An app import is a relative module, an `@/`, `~/` or `#` alias, an `@elmeragroup/*` module other than the intl packages, or a module named by any scheme other than `node:`, `bun:`, `deno:`, `npm:` and `jsr:` (a `file:` URL, Vite's `virtual:` modules, an app's own scheme). Such a `t` may be the package's translator returned by a wrapper that extraction never reads, such as a module outside `include`. Before, its messages were silently left out of the catalogs and shipped untranslated. The failure names the import. In a file that does not import `@elmeragroup/intl` (not even a type), a `t` from an import the classifier reads as an npm package by the specifier's shape (`react-i18next`, `next-intl`, `i18next`; `@acme/_i18n` reads as an app import) still passes, as do a parameter and a function written in the file. A file that imports the package keeps its stricter check, by the README's receiver rules: there `const { t } = useTranslation("ns")` passes and `useTranslation(ns)` with `ns` a parameter fails, as before. A module named by a runtime or registry scheme (`node:`, `bun:`, `deno:`, `npm:`, `jsr:`) now counts as an npm package everywhere, so `import { test as t } from "bun:test"` passes and a `.t(…)` on such an import (`i18next.t("k")` from `npm:i18next`) is no longer reported; every other scheme stays an app import. A registry scheme naming the intl packages (`npm:@elmeragroup/intl@1.2.3/react`, `jsr:@elmeragroup/intl/react`, as Deno imports them) is the package itself everywhere, so their translators are extracted and their namespace imports and re-exports fail as the bare specifier's do; before, they were not recognised as the package.

Code that extraction used to accept now fails: an app module wrapping another library's translator, as i18next's App Router setup does (`const { t } = await useTranslation(lng)` from `../i18n`). Builds of such an app fail until each of those files applies a remedy from the README's migration section:

- in a file whose only i18n is that translator, list the file in `exclude` in `elmera-intl.json` and turn `elmera-intl/extractable` off for it in `.oxlintrc.json` (escaping a Next.js segment's `[` as `[[]` in both), or rename the translator (`const { t: i18nT } = …`);
- in a file that also imports the package, expose the translator from the legacy module under another name (an adapter such as an async `legacyT(lng)` on the server or a `useLegacyT()` hook on the client, in a module with no import of the package, not even a type-only one), which is the whole remedy; or split the file and give the new legacy-only file one of the remedies above.

The message for an untraced bare `t(…)` in a file that imports the package changes: it tells a translator from `useT()` or `getT()` apart from an IntlInstance's `.t`, and gives `const { t } = await getIntl()` for a `t` bound to an instance.
