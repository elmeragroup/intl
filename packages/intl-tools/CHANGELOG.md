# @elmeragroup/intl-tools

## 0.1.0

### Minor Changes

- d9163e8: `@elmeragroup/intl/effect`: `CurrentIntl`, the translator as an Effect service (`const { t } = yield* CurrentIntl`), provided per request by `CurrentIntl.provide(options)` or once by `CurrentIntl.layer(options)`, with `effect` (`^4.1.3`) as an optional peer. The extractor and the `elmera-intl/extractable` lint rule read `yield* CurrentIntl` as a bound IntlInstance and reject any other read of the service.
- c687582: First public release: the source-keyed runtime with its Next.js and TanStack Start adapters, and the build-time tools (extractor, `elmera-intl` CLI, PO catalogs, compiler and loaders, Vite and Next plugins, the `elmera-intl/extractable` lint rule and the Vitest catalog check).
- e6ae286: Extraction and the `elmera-intl/extractable` lint rule fail a bare `t(…)` call whose `t` is rooted in an app import, in every file, including files that do not import `@elmeragroup/intl`. An app import is a relative module, an `@/`, `~/` or `#` alias, an `@elmeragroup/*` module other than the intl packages, or a module named by any scheme other than `node:`, `bun:`, `deno:`, `npm:` and `jsr:` (a `file:` URL, Vite's `virtual:` modules, an app's own scheme). Such a `t` may be the package's translator returned by a wrapper that extraction never reads, such as a module outside `include`. Before, its messages were silently left out of the catalogs and shipped untranslated. The failure names the import. In a file that does not import `@elmeragroup/intl` (not even a type), a `t` from an import the classifier reads as an npm package by the specifier's shape (`react-i18next`, `next-intl`, `i18next`; `@acme/_i18n` reads as an app import) still passes, as do a parameter and a function written in the file. A file that imports the package keeps its stricter check, by the README's receiver rules: there `const { t } = useTranslation("ns")` passes and `useTranslation(ns)` with `ns` a parameter fails, as before. A module named by a runtime or registry scheme (`node:`, `bun:`, `deno:`, `npm:`, `jsr:`) now counts as an npm package everywhere, so `import { test as t } from "bun:test"` passes and a `.t(…)` on such an import (`i18next.t("k")` from `npm:i18next`) is no longer reported; every other scheme stays an app import. A registry scheme naming the intl packages (`npm:@elmeragroup/intl@1.2.3/react`, `jsr:@elmeragroup/intl/react`, as Deno imports them) is the package itself everywhere, so their translators are extracted and their namespace imports and re-exports fail as the bare specifier's do; before, they were not recognised as the package.

  Code that extraction used to accept now fails: an app module wrapping another library's translator, as i18next's App Router setup does (`const { t } = await useTranslation(lng)` from `../i18n`). Builds of such an app fail until each of those files applies a remedy from the README's migration section:

  - in a file whose only i18n is that translator, list the file in `exclude` in `elmera-intl.json` and turn `elmera-intl/extractable` off for it in `.oxlintrc.json` (escaping a Next.js segment's `[` as `[[]` in both), or rename the translator (`const { t: i18nT } = …`);
  - in a file that also imports the package, expose the translator from the legacy module under another name (an adapter such as an async `legacyT(lng)` on the server or a `useLegacyT()` hook on the client, in a module with no import of the package, not even a type-only one), which is the whole remedy; or split the file and give the new legacy-only file one of the remedies above.

  The message for an untraced bare `t(…)` in a file that imports the package changes: it tells a translator from `useT()` or `getT()` apart from an IntlInstance's `.t`, and gives `const { t } = await getIntl()` for a `t` bound to an instance.

- 0f54eb3: Extraction and the `elmera-intl/extractable` lint rule fail an IntlInstance used as a value in the file that binds it ([#40](https://github.com/elmeragroup/intl/issues/40)). Before, a page could hand its instance to a child (`<Row intl={intl} />`), and a child that does not import `@elmeragroup/intl` read `const { t } = intl` unchecked: its messages were silently left out of the catalogs and shipped untranslated, with `check` green. Now an instance bound from `useIntl()`, `getIntl()`, `createIntl()` or `yield* CurrentIntl` may only be read through its own members (`t`, `format`, `locale`, `timeZone`, `catalog`, `formats`), bound by a declaration that is not exported, cleared by a plain assignment (`intl = undefined`; a compound one, `intl ??= other`, reads it and fails), listed in a dependency array, spread into an object (`<Row {...intl}>` under the automatic JSX runtime, or given as the props of a `createElement` bound to a `react` import, which copies them), or discarded (`await getIntl();`, `void getIntl()`). The failure is at the parent, names the expression (`intl`, `useIntl()`, `createIntl(…)`, `yield* CurrentIntl`) and the fix. The files that receive an instance read as before.

  Code that extraction used to accept now fails. Each form, and its rewrite:

  - an instance passed as a JSX prop (`<Row intl={intl} />`) or a call argument (`formatDue(intl, d)`, `render(yield* CurrentIntl)`): call `useT()` or `useIntl()` in the child, or pass `intl.format`, `intl.locale` or `msg()` descriptors;
  - a context value (`<Ctx.Provider value={intl}>`, an outlet's `context={intl}` or `context={{ intl }}`): render `<IntlProvider {...config}>`, nested where a child needs another locale, and call `useIntl()` or `useT()` in the child;
  - an instance stored in state, a ref or an object (`setI(createIntl(cfg))`, `useState([intl])`, `r.current = intl`, `box.intl = intl`, a request context `{ intl: createIntl(cfg) }`): store the config, and call `createIntl(config)` where it is used;
  - an instance returned (a local factory, `useMemo(() => createIntl(cfg), [cfg])`): render `<IntlProvider>` and call `useIntl()`, or return the config;
  - an instance exported (`export const intl = createIntl(cfg)`, `export { intl }`, `export default intl`): export the config, and call `createIntl(config)` where it is used;
  - an instance passed as the props of a hand-written `jsx(Row, intl)` (from `react/jsx-runtime`, which keeps the object itself as the props): pass `{ ...intl }` if the child needs the config;
  - an instance as a JSX child (`<Box>{intl}</Box>`): render a member (`{intl.locale}`), or bind it in the child;
  - an instance chosen rather than bound (`cached ?? createIntl(cfg)`, `x ? await getIntl() : undefined`, `x ?? useIntl()`, a pattern default such as `function f({ intl = createIntl(cfg) })`), which now fails at the factory's call even when only a member such as `.locale` is read (a `.t(…)` on the result already failed as untraced): choose the config first, then bind (`const intl = createIntl(cached ?? cfg)`);
  - an instance on the right of a plain assignment (`let i; i = createIntl(cfg)`): bind it in the declaration, `const i = createIntl(cfg)`;
  - an instance logged, compared or inspected (`console.log(intl)`, `intl === other`, `typeof intl`, `!intl`, `` `${intl}` ``, `intl.valueOf()`, `intl.toString()`): compare or log a declared member (`intl.locale`);
  - an instance given to `Object.assign` (`Object.assign({}, intl)`): `{ ...intl }` is the copy; given to `Object.values` or `Object.entries`: read the member by name;
  - `.then`, `.catch` or `.finally` on an un-awaited `getIntl()` (`getIntl().then(…)`, `getIntl().catch(…)`, `const p = getIntl(); p.then(…)`), or `getIntl()` inside `Promise.all`: `const intl = await getIntl()`, or a helper that awaits it and returns the member it needs (`async function money() { const { format } = await getIntl(); return format; }`, then `const [format, data] = await Promise.all([money(), load()])`);
  - an instance passed to an Effect layer or service (`Layer.succeed(CurrentIntl, createIntl(cfg))`, which already failed at `CurrentIntl`): `CurrentIntl.layer(options)` or `CurrentIntl.provide(effect)`;
  - a factory's call in a dependency array (`useEffect(f, [useIntl()])`): bind it, then list `[intl]`.

  Tests and stories fail too: `elmera-intl/extractable` runs on every file it lints, test files that `include` leaves out as well. `renderHook(() => useIntl())` returns the instance from the callback, so it now fails at `useIntl()`: return the member the test needs (`renderHook(() => useIntl().locale)`). A unit test that hands `createIntl(cfg)` to a component (`render(<Row intl={createIntl(cfg)} />)`) renders the component inside `<IntlProvider {...cfg}>` instead, and the component calls `useIntl()` or `useT()`.

  Under the classic JSX runtime, `<Row {...intl}>` with the spread as its only attribute compiles to `factory(Row, intl)`, handing the factory the instance itself. React's `createElement` copies the props, so the spread passes when the factory is bound to a `react` import (`import React from "react"`), and under the automatic runtime it compiles to a copy and passes. It now fails, where it passed before, in the two configurations that need the `@jsxRuntime classic` pragma and name another factory: `React` as a global (`/** @jsxRuntime classic */` with no `react` import), and a `@jsx` factory such as preact's `h` (`/** @jsxRuntime classic */ /** @jsx h */` with `import { h } from "preact"`), where the extractor cannot prove the factory is React's, and a factory that keeps the object by reference (as React 19's own `jsx()` does) gives the child its `t` unextracted. Neither is a supported setup (the React peer is `^19.0.0`, which needs the automatic runtime; preact is not a peer). The failure names the rewrite: copy it yourself, `<Row {...{ ...intl }}>`, or use the automatic runtime (or import `React`). Extraction reads a file without the pragma as the automatic runtime, whatever the build is configured with.

  `[t]` and `[intl]` are a dependency array by one rule, by how the hook is bound. A hook bound to a `react` import (named, renamed, or `React.x` through React's default or namespace import) is one only for `useEffect`, `useLayoutEffect`, `useInsertionEffect`, `useMemo`, `useCallback` and `useImperativeHandle`, at their dependency argument, the last: so `React.useEffect(f, [t])`, `React.useCallback(f, [t])` and `import { useMemo as memo } from "react"; memo(f, [t])` now pass. Any other bare `use*` callee is one when it is called with two or more arguments, the array last, as before, so a custom effect hook (`useAsync(f, [t])`) keeps passing. Newly failing, each with `` `t` is passed or stored `` (or the instance message for `[intl]`):

  - `[t]` or `[intl]` in a single-argument `use*` call (`useState([t])`, `useRef([t])`, `useEffect([t])`): state is not a translator's place; put a dependency array at the dependency argument;
  - in React's `useState`, `useReducer` (`useReducer(r, [t])`) or `useRef`, renamed or not (`import { useState as useS } from "react"; useS(0, [t])`);
  - at the wrong slot (`useImperativeHandle(ref, [t])`): put it at the dependency argument;
  - in a member facade (`Hooks.useEffect(f, [intl])`, which `[t]` already failed): call React's hook, or `useCallback(f, [t])` and pass the facade `[cb]`.

  A bare `use*` callee not imported from `react` that keeps its last argument (a custom hook such as `useStore(cb, [intl])`, a React hook re-exported through an app module, `preact/hooks`) still passes, and a `{ t }` read from what it keeps, in a file that does not import the package, extracts nothing: the README lists it as a residual. Closing it would fail every custom effect hook, and closing it after 1.0 would be a breaking change.

  A specifier of `export … from "…"` and `export * as name from "…"` name the other module's binding, so `export { t as x } from "./other"` and `export * as t from "./other"` beside a bound `t` in the same file no longer fail. `export { t }` of a bound `t` now reports once, as ``exporting `t` hides its call sites``, not twice. `import.meta` and `new.target` are no longer read as a binding named `meta` or `target`, so `const meta = useT()` beside `import.meta.url` no longer fails as `` `meta` is passed or stored ``.

- b22f7bc: `withIntl` now returns Next's phase function, `(phase) => config`, in place of the config, and refuses a project it cannot read only in the phases that compile through Turbopack: `next build` and `next typegen`, `next dev` and a dev custom server, and `next analyze`. There the refusals and their messages are as before. Every other phase compiles nothing, so there `withIntl` reads nothing and returns the config as passed, the very object: `next start` and a production custom server do not read the project, so a pruned deployment starts without `elmera-intl.json` or its source, or as a user who cannot read them, and with catalogs that lie outside the root Next detects there (before, `next start` exited with `withIntl: the catalogs … are outside the Turbopack root …`).

  `export default withIntl(config, options)` in `next.config.ts` is unchanged. Code that read the result as a config changes:

  - a config that is itself a phase function calls the result inside it: `export default async (phase, context) => withIntl(await config(phase, context), options)(phase)`;
  - a wrapper applied outside `withIntl` (`withMDX(withIntl(config, options))`) moves inside it (`withIntl(withMDX(config), options)`), as the README already asked: it would now get a function;
  - a test or tool that reads the rule or alias calls the result with a phase, such as `withIntl(config, options)("phase-production-build")`.

  A `turbopack.resolveAlias` entry mapping the request module to `withIntl`'s own target is now refused like any other: it was allowed for a config wrapped twice, which a function result rules out. Remove it and set the `request` option.

- 351f3a2: `@elmeragroup/intl/core`: `negotiateLocale(acceptLanguage, locales, { aliases })`, the most preferred of an app's locales an Accept-Language header accepts (RFC 9110 §12.4.2 weights, RFC 4647 §3.4 lookup), written as in `locales`, or `undefined` for the app's default, with the `NegotiateLocaleOptions` type. Aliases (`{ no: "nb", nn: "nb" }`) are case-insensitive and checked along the lookup chain after the locales themselves. A range rejected with `q=0` excludes the locale it names on every path and its alias target only through an alias, so `nb-NO, nb;q=0` and, with those aliases and no `no` shipped, `nn, no;q=0` are not Bokmål, but `nb, no;q=0` is; `*` is the caller's default at any weight. A wrong configuration (an alias naming a locale not in the list, an alias that is not a concrete language range, two locales differing only in case) throws a `RangeError` on every call. The example apps negotiate with it in place of their own copies.

### Patch Changes

- d9163e8: The PO reader and writer are now `@elmeragroup/intl-tools`' own Effect `Schema` codec, replacing the `po-parser` dependency with `effect` (4.1.3). Catalogs read and write as before: the same GNU msgcat reading, held by po-parser 2.2.0's ported test suite and its recorded output (`test/po-conformance`).
- 5b4b4b6: `vite build --watch` with `intl()` rebuilds when a source the check read changes, so repairing the source that failed
  the check clears the failure on the next rebuild. Before, a check that failed before the build loaded a module left only
  the config, the catalogs and the formats module watched, and a source the build never imports was never watched. The
  build now watches each source file the check read, and the target of a symlinked one, but none in an output directory
  (`build.outDir`, or an output `dir` of `build.rolldownOptions`, resolved against
  the bundler's working directory as the bundler resolves it; a bundle the config's `include` may match), so a build
  never rebuilds on its own output; a source created later is not watched yet (#64).
- 8f161b6: During `vite dev`, an edit to `elmera-intl.json` invalidates a compiled PO import, so its next load compiles with the
  edited config. On Next, the loader now registers `elmera-intl.json` as a dependency of an import that fails on the
  config or on a PO of no configured locale. A PO of no configured locale fails with one text on both hosts: Next's swaps
  the absolute path for the path relative to the config, and Vite's gains the `elmera-intl:` prefix.
- b7a6e6a: `extract`, `extract --watch` and the Vite dev watch do what they did, with one exception: a watch (the CLI's or
  Vite's) that fails while recording what a sync wrote now reports `Failed` with one `SyncFailed` problem naming the
  error, and stays running, where it used to stop. The next relevant change starts another sync, a change to a catalog
  that sync already wrote included.
- 42bd10c: An absolute `catalogs` pattern with a `..` through a directory that does not exist (`/app/messages/missing/../{locale}.po` with no `messages/missing`) now fails `extract`, the watch's sync and `check` with `CatalogClimbsMissing`, naming the directory, and writes and creates nothing. Before, on a fresh tree, the write created the directory and wrote through it, which could replace an existing catalog the path then reached (`messages/nb.po`) with one merged from none, and `check` reported that catalog as missing.
- ced467d: Catalogs reached through a link compile. A `*.po` import is a configured catalog when its file is one at the path the config names or at its real path, on Next and on Vite: the bundler hands over the file it resolved through its links, so catalogs named through a link inside the project (`intl-link -> intl`), or a config reached through a directory alias (`/tmp/…` for `/private/tmp/…` on macOS), failed with `… is not a configured catalog`. On Next, `withIntl` also builds the rule's path from the catalogs' real path below the root's, as Turbopack matches it, so it no longer refuses such catalogs as outside a root that holds them (before, the rule never matched either: `Unknown module type`). Catalogs written inside the root through a link out of it are left to Turbopack, which refuses such an import itself. A file that the catalogs of several locales link to is the catalog of none, as before.
- abe7b0c: The config refuses catalog paths that two locales could share, as `ConfigInvalid` in every host: a locale that is not an identifier `Intl.getCanonicalLocales` accepts (a path such as `/nb` or `../messages/nb` named another locale's catalog), two locales that are one identifier (`nb` and `NB`, `iw` and `he`), and a `catalogs` pattern with a `..` segment anywhere after the first segment holding `{locale}` (`messages/{locale}/../catalog.po`), where a directory the sync created for one locale made its path reach the catalog another locale had just written and `extract` replaced its translations. A `..` before `{locale}` stays valid.
- 089b2ad: A config reached through a link to its directory means one thing to every tool. Its root is now the real path of the directory its path names, so `extract`, `check`, the watch, `intl()` and `withIntl` resolve every relative path in it, `formats` as well as `catalogs`, from one place: with `/mnt/web -> /repo/apps/web`, `"../messages/{locale}.po"` in `/mnt/web/elmera-intl.json` is `/repo/apps/messages` for each, where `withIntl` and the catalog import looked in `/mnt/messages` and `extract --config /mnt/web/elmera-intl.json` wrote there. The real path is the one Next and Vite resolve: the kernel's on POSIX, so a directory spelled in another case on a volume that folds case, or a link whose target climbs with `..` through another link, roots where the kernel and the hosts put it, and Node's own resolution on Windows, which keeps a mapped drive. Each read of the config takes its text and its root from one directory, so a link repointed during the read never pairs one checkout's config with another's root. An absolute `catalogs` pattern climbing out of a link with `..` is read where the kernel takes it by `withIntl`'s rule and the catalog import too, as `extract` writes it. An absolute pattern whose `..` follows a directory that does not exist, which `extract` refuses (`CatalogClimbsMissing`), is no catalog to the import either. `extract --watch` restarts when a link to the config's directory is repointed, the config's text unchanged, and names what it writes from the new root. A symlinked `elmera-intl.json` keeps the directory its link is in as its root, as before. `withIntl` also takes the app directory at its real path, as Next's CLI does (`next dev`, `next build`, `next start`): with `dir` a link straight to a workspace app and no root set, its rule now matches the catalogs below the workspace root Next uses, and with `next` hoisted to the workspace, the PO loader still gets Turbopack's roots, where it got none and checked nothing. A custom server's `next({ dir })` takes `dir` as given, which `withIntl` cannot see: give it the app's real directory.

  Before the first `extract` after upgrading, a project whose `catalogs` climbs with `..` from a directory reached through a link should compare the directory its catalogs were written in with the one they resolve to now, and move or merge its translated PO files there: `extract` writes a new PO where none is, and a newly extracted PO cannot recover the translations left in the old one. Printed paths, and the absolute paths scripts read from `extract --json` or from the watch's output, now use the real spelling (`/private/tmp` for `/tmp` on macOS). To give two directories that link to one app their own siblings, make each a real directory holding a symlinked `elmera-intl.json`.

  locale, a changed `include` or `catalogs`) and recompiles every PO import, without restarting the dev server, as

  result, for every PO save as Vite's watcher reports it, during a restart included, whether or not the restart's watch

  ended` and the failure as its cause; during the server's close it is logged instead of being dropped. That now includes
  a logger that throws on a result and again on its `SyncFailed` during a restart, and a watcher that fails to close as
