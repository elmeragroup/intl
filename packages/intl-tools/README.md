# @elmeragroup/intl-tools

Build-time tools for [`@elmeragroup/intl`](../intl/README.md): the deny-by-default extractor, the `elmera-intl` CLI that writes and checks PO catalogs, the catalog compiler and the loaders that run it on `*.po` imports (Next, Vite, Node), the `elmera-intl/extractable` oxlint rule and a Vitest global setup. Everything here parses source or ICU, so none of it ships to a browser. It shares the runtime's serializer, wire-key hash and catalog codec (`/internal/*`), so the extracted keys are the runtime's keys and a catalog that checks compiles and formats as the runtime will.

## Extraction contract (deny-by-default)

In a file that imports `@elmeragroup/intl` (including `import type`), only these forms are allowed; anything else fails extraction and lint, with a message naming the fix. Names resolve lexically, as JavaScript does (function, block, loop head, catch, class and switch scopes; `var` hoisted to its function body or static block; parameter defaults and a switch's discriminant resolve outside the body and cases next to them), so a shadowing `t`, `T`, `msg` or `Fragment` is not the package's. A computed key that resolves statically (a string or number literal, an expression-free template, or a `const` bound to one) is the named key: `i["t"]("x")` is `i.t("x")`.

The lint rule and `check` catch a `<T>` inside a `<T>` as it is written; for code they do not see, the runtime is the backstop for an element of the same loaded `T` function at any depth: it reports to `onError` and renders the children as written. It does not see a wrapper component that renders a `<T>`, a second loaded copy of the package, or, in a Next server component, a client-reference `<T>`, which it reads as a tag.

A `.t(…)` call is checked by its receiver's provenance, in every file, importing or not (an IntlInstance may arrive as a parameter, from code extraction never reads or through a custom hook that keeps its dependency array; see the residuals):

- Traced: bound from `useIntl()`, `(await) getIntl()`, `createIntl()` or `yield* CurrentIntl` in this file, or an alias of one. Extracted.
- Unrelated, only when proven: a value written in this file (a function or class, a primitive, or an object or array literal without getters holding only unrelated values), or an npm package's import itself (`i18next.t("k")`; a module named by a runtime or registry scheme, `node:`, `bun:`, `deno:`, `npm:` or `jsr:`, counts as one, unless it names the intl packages, as Deno's `npm:@elmeragroup/intl@1.2.3/react` and `jsr:@elmeragroup/intl/react` do, which are the packages themselves, and any other scheme, such as `file:` or Vite's `virtual:`, is an app import), through `await` and `const` initializers. Ignored, and a `{ t }` pattern over it is allowed.
- Derived: an npm package's import read through members, destructured without defaults, or called with only inline data arguments (primitives, and object or array literals of them). It may hold an IntlInstance handed to it by code extraction never reads, or kept from its dependency array by a `use*` hook not imported from `react` (`useStore(cb, [intl])`, a residual below); an instance this file hands it any other way (`setI(createIntl(cfg))`) fails where it is bound, below. So a `.t(…)` on it is untraced. An instance or translator bound in code extraction scans reaches it through that same residual, and fails where it is handed on any other way; one that arrived from code extraction never reads may be passed on, and that code can hand it one through any wrapper (a workspace package outside `include` whose specifier reads as an npm package by its shape, such as `@acme/ui`, exposing `useCompanyTranslation()` that returns `{ t }` from `useT()`), the residual rows on code outside `include`, on an instance passed on and on scopes that look like npm packages below. So a `{ t }` pattern over it and a bare `t(…)` bound from it are allowed (`const { t } = useTranslation()`), and a `t` either route carries is not caught.
- Untraced: anything else: a parameter, a global, `this`, a `let` or `var`, a value derived from an npm import (above), a binding with a default (`const { i = createIntl(cfg) } = o`), a local function's result, a member or projection of a local object (`box.i = createIntl(cfg)`, then `box.i` or `const { i } = box`), an npm call given a function, a named container or any other non-data argument (`useMemo(() => createIntl(cfg))`, `useMemo(make, [])`), and a relative, aliased or `@elmeragroup/*` import, which may export an IntlInstance. Fails, naming the receiver: bind the instance in the file, or translate a `msg()` descriptor with `.t.from(d)`, which is allowed on any receiver. Such a value holds an IntlInstance only from code extraction never reads, through the custom-hook residual, or by a store in this file, which fails where the instance is bound (`box.i = createIntl(cfg)` fails at `createIntl(cfg)`).

In a file that imports the package, an IntlInstance is bound where it is used, as `t` is: an identifier bound from `useIntl()`, `(await) getIntl()`, `createIntl()` or `yield* CurrentIntl`, or such a call itself, may only be read through a member it declares (`t`, `format`, `locale`, `timeZone`, `catalog`, `formats`), bound by a declaration that is not exported, cleared as the target of a plain assignment (`intl = undefined`, which writes the binding; `intl ??= other` reads it, so it fails), listed in a dependency array as `[t]` is, spread into an object (which copies the config and never `t`), given as the props of a `createElement` bound to a `react` import (which copies them as a spread does), or discarded (`await getIntl();`, `void getIntl()`). Any other factory may keep the object itself as the props, as the automatic runtime's `jsx(Row, intl)` does, so the instance fails there as any argument does. So `<Row {...intl}>` passes under the automatic JSX runtime, where it compiles to a copy, and under `@jsxRuntime classic` with `import React from "react"`; it fails in a file with the `@jsxRuntime classic` pragma whose factory is `React` as a global or a `@jsx` pragma's (`/** @jsx h */` with preact's `h`), where it compiles to `factory(Row, intl)`, a factory the extractor cannot prove is React's, and the failure says so. Both passed before this release, so this is a breaking change, in configurations the packages do not support (the React peer, `^19.0.0`, needs the automatic runtime; preact is not a peer): copy it yourself, `<Row {...{ ...intl }}>`, or use the automatic runtime (or import `React`). Extraction reads a file without the pragma as the automatic runtime, whatever the build is configured with. Any other use fails where it is written, naming the expression: a JSX prop (`<Row intl={intl} />`), a context value (`<Ctx.Provider value={intl}>`, an outlet's `context`), a call argument (`Object.values(intl)` too), a store (`useState([intl])`, `setI(createIntl(cfg))`), a returned value, an export (`export const intl = createIntl(cfg)`, `export { intl }`), `typeof`, a template, `.then` on `getIntl()`'s promise, and `.valueOf()`, which returns the instance. The file an instance reaches cannot tell its `t` from another library's, and one that does not import the package is not checked, so the failure is where the instance is bound. Bind one where it is used: `useT()` or `useIntl()` in the child (a nested `<IntlProvider {...config}>` gives a child another locale), `await getIntl()`, `yield* CurrentIntl` provided by `CurrentIntl.layer(options)` or `CurrentIntl.provide(effect)`, or `createIntl(config)` with the config passed; or pass its `format`, its `locale` or `msg()` descriptors. To read `getIntl()` beside other work, await it in a helper that returns the member it needs: `async function money() { const { format } = await getIntl(); return format; }`, then `const [format, data] = await Promise.all([money(), load()])`. `[t]` or `[intl]` is a dependency array as the `t` row says: a custom effect hook (`useAsync(f, [t])`) keeps passing, a React hook that may keep the array (`useState`, `useRef`, `useReducer`) or a member of an app module (`Hooks.useEffect(f, [t])`) fails, and a factory call in the array (`[useIntl()]`) fails.

A bare `t(…)` call is checked in every file, importing or not, by where its `t` is rooted. It fails when `t` is rooted in an app import: a relative module, an `@/`, `~/` or `#` alias, an `@elmeragroup/*` module other than the intl packages, or a module named by any scheme other than `node:`, `bun:`, `deno:`, `npm:` and `jsr:` (`file:`, `virtual:i18n`). The walk follows `await`, `yield*`, the initializer of any `const`, `let` or `var` declaration of the name (destructured or not), the right-hand side of a plain `=` assignment (a TypeScript namespace's `export const t = …` compiles to one), a member's object, and a call's or `new`'s callee, whatever its arguments. Such a `t` may be the package's translator, returned by a wrapper that extraction never reads (a module outside `include`), so its messages would ship untranslated. The failure names the import. In a file that does not import the package (not even a type), that is the only check: a `t` rooted in an import the classifier reads as an npm package (by the specifier's shape: `@acme/_i18n` is a valid npm name, but reads as an app import) (`useTranslation(ns)` from `react-i18next`, `import { t } from "i18next"`) or in a runtime or registry module (`import { test as t } from "bun:test"`) passes, as do a parameter, a global and a function written in the file. In an importing file, a bare `t(…)` is also checked against `useT()`/`getT()`, as a `.t(…)` receiver is checked above: any `t` that may hold a translator and is not bound from a factory fails, a parameter included, even when the file's only import of the package is a type. There another library's `t` passes only when it is unrelated or derived by the receiver rules above: `const { t } = useTranslation("ns")` passes, but `useTranslation(ns)` with `ns` a parameter is untraced, so its `t` fails. A `t` bound to an IntlInstance itself (`const t = await getIntl()`) is not a translator: destructure it, `const { t } = await getIntl()`. An app module that wraps another library's translator fails the same way; see [Migrating from another library](#migrating-from-another-library).

In an importing file, a computed key that does not resolve statically may be `t`. In a destructuring pattern it fails. On a member access it fails when the receiver is an IntlInstance the extractor infers: bound from `useIntl()`, `createIntl()` or `(await) getIntl()`, or an alias of one (`i[key]`, `createIntl(cfg)[key]`, `Reflect.get(i, key)`). On any other receiver (a record lookup such as `LABELS[key]`, `criteria[field] = v`, `const { logo } = BRANDS[brand]`) the read is allowed. `Reflect` may only be called directly, and `Reflect.get(x, "t")` fails on any receiver. An IntlInstance's `t` is not enumerable, so an object spread or a rest never carries it; handed to `Object.assign`, `Object.values` or `Object.entries`, the instance fails as any argument does. Destructuring defaults and computed keys are checked like any other code.

Residuals (not caught). A row marked _outside an importing file_ is a limit of the app-import walk: in a file that imports the package, even only a type, the same `t` fails the `useT()`/`getT()` check.

## Migrating from another library

An app moving from i18next (or another library) often wraps the old translator in an app module, as i18next's App Router setup does: `const { t } = await useTranslation(lng)`, from `../i18n`. Extraction fails each such `t(…)`, because it cannot tell that `t` from the package's translator returned by a wrapper. Choose the remedy by what the file holds:

- **A file whose only i18n is the legacy translator** (it does not import the package): list it in `exclude` in `elmera-intl.json`, and turn `elmera-intl/extractable` off for it in `.oxlintrc.json`. This switches off every extraction check in the file, including an untraced `intl.t(…)`, so it fits only such a file.
  - List exact files, or `/**` globs, never a bare directory: `src/legacy` passes `check` but still fails lint.
  - Escape a bracket's `[` as `[[]`, in both lists: both read `src/app/[lng]/page.tsx` as a glob class, which matches `src/app/l/page.tsx` and not the file itself. Write `src/app/[[]lng]/page.tsx`.
  - Each list is relative to its own config: `exclude` to `elmera-intl.json`, and `overrides[].files` to `.oxlintrc.json`. With a root `.oxlintrc.json` and an app's own `elmera-intl.json`, the lint glob carries the app's directory.
  - Every `include` pattern must still match a file, or `check` fails with `IncludeUnmatched`.
  - When the file first imports the package, remove it from both lists.
- **Rename the translator** in a file that does not import the package: `const { t: i18nT } = await useTranslation(lng)`, then `i18nT("title")`. That is one edit at the binding and one at each call.
- **A file that imports the package is never excluded.** Have the legacy module expose the translator under another name, as an adapter. On the server it is an async helper over i18next's non-hook server API, imported under a name that is no hook's (`import { useTranslation as getLegacyTranslation } from "./i18n"`): `export async function legacyT(lng: string) { return (await getLegacyTranslation(lng)).t; }`, bound as `const i18nT = await legacyT(lng)`. On the client it is a hook: `export function useLegacyT() { return useTranslation().t; }`, with react-i18next's `useTranslation`, bound as `const i18nT = useLegacyT()`. The adapter lives in a module with no import of the package, not even a type-only one: in an importing module, reading `.t` off the wrapper's untraced result fails. That is the whole remedy, and the file's intl code stays checked. Or split the file: the part using the package stays checked, and the new legacy-only file still fails until it gets one of the remedies above, an exclusion or a rename. Destructuring `{ t: i18nT }` from the app module does not work in an importing file: a `t` key destructured from an untraced value fails. From an npm hook, such as react-i18next's own `useTranslation()`, it passes when the hook is derived by the receiver rules above (only data arguments: `useTranslation("ns")`, or `useTranslation(ns)` with `const ns = "checkout"`, but not with `ns` a parameter).

In a monorepo with one root `.oxlintrc.json`, an app's legacy file is listed in both configs:

```text
.oxlintrc.json                  "overrides": [{ "files": ["apps/web/src/app/[[]lng]/page.tsx"],
                                                "rules": { "elmera-intl/extractable": "off" } }]
apps/web/elmera-intl.json       "include": ["src/**/*.{ts,tsx}"], "exclude": ["src/app/[[]lng]/page.tsx"]
apps/web/src/app/[lng]/page.tsx import { useTranslation } from "../../i18n";
                                const { t } = await useTranslation(lng);
```

## CLI

`elmera-intl extract | check [--json] [--config <path>]` and `elmera-intl extract --watch [--poll <ms>] [--config <path>]`, configured by `elmera-intl.json` in the working directory:

```json
{
  "include": ["src/**/*.{ts,tsx}"],
  "exclude": ["**/*.test.tsx"],
  "catalogs": "messages/{locale}.po",
  "locales": ["nb", "sv"],
  "formats": "src/intl-formats.ts"
}
```

Each locale has a catalog of its own: a locale is an identifier `Intl.getCanonicalLocales` accepts (`nb`, `pt-BR`; never a path, and not every BCP 47 tag: `en-GB-oed` is refused), listed once (`nb` and `NB`, or `iw` and `he`, are one locale), and `catalogs` may hold no `..` segment anywhere after the first segment holding `{locale}` (`messages/{locale}/../catalog.po`), because a directory the sync creates for one locale could then make its path reach another locale's catalog. A `..` before `{locale}` is allowed. Each fails as `ConfigInvalid` in every host. A relative pattern is joined onto the root, which collapses its `..` (`messages/jump/../{locale}.po` is `messages/{locale}.po`), so only an absolute pattern reaches the file system with one, which resolves it from where the kernel says. A catalog that does not exist through such a path, while a directory before a `..` in it does not exist either (`/app/messages/missing/../{locale}.po` with no `messages/missing`; a dangling link counts as missing), fails `extract`, the watch's sync and `check` with `CatalogClimbsMissing`, writing and creating nothing: creating that directory would change the file the path reaches, so the write could replace a catalog the read never saw. Whether the `..` would climb back to the same place is not worked out. The problem names the directory as the path spells it (`messages/jump/../fresh`, never a normalised `messages/fresh`). Create it (or, when it is a link, its target), or write the pattern without the `..`; a running watch syncs again on the next change to a source.

`formats` (optional) names the module whose `formats` export is the app's `formats`: `export const formats = { … } satisfies Formats`, with type-only imports and JSON option values (a separate Node process evaluates it). A value JSON does not carry (`Infinity`, `NaN`, `undefined`, a function, symbol, bigint, `Date` or class instance) fails with `FormatsInvalid` naming its path, because the formats reach the runtime through JSON. The app's adapter imports it, and `check` and every loader load it (Node, with type stripping), so all three format with one definition. Each load reads the module again and re-evaluates it when its content changed, evaluating exactly the text it read, so a running dev server or watch build picks up an edit.

`include` decides which files reach the catalogs: a `<T>` in a file it does not match is never extracted, `check` stays green, and the page renders English. Keep it as wide as the app's source directories, not a hand-kept list of files. Each include pattern must match at least one file (`IncludeUnmatched`), so a renamed directory fails instead of dropping its messages; directories matching a pattern (a folder named `x.tsx`) are skipped.

- `extract` writes one PO per locale (msgid = English source, msgctxt = context, `#.` = what each tag stands for, `#:` = files, without line numbers), and nothing else: the PO is the only checked-in catalog. Translations and flags are kept; entries no source uses are dropped; nothing is written when any source fails or an include pattern matches no file.
- `check` fails (exit 1) on: an extraction failure, a catalog missing or unreadable, a serializer version mismatch, a message missing from or obsolete in a catalog, an untranslated entry, a translation identical to its source (`TranslationIdenticalToSource`, compared exactly: an msgstr left in English renders English; an entry flagged `#, ignore-same`, Weblate's flag for the same check, is English on purpose, and that flag on a translation that differs fails as `IgnoreSameUnused`), a msgid or msgstr that does not compile, placeholder or tag mismatch, an argument formatted as another kind than in the source (`ArgumentKindMismatch`: an argument the source uses as text, plain `{x}` or select, stays text; a number stays number, plural or selectordinal; a date stays date or time. `{name}` as `{name, number}` renders NaN, and a plain `{x}` takes text only, so a number or date shown plainly fails at runtime), an argument one message (source or translation) uses as two kinds of value, such as `{n}` in one branch and `{n, number}` in another (`ArgumentKindConflict`: no one value renders in every use; `{n, number}` everywhere or `#` passes), two messages whose wire keys collide (`KeyCollision`: give one a context), an include pattern that matches no file, and, once all of that passes, each locale's compiled catalog (and the English one) failing to compile or dry-format with the configured `formats` (`TranslationUnformattable`, `SourceUnformattable`: an option `Intl` rejects, such as an unknown currency in a skeleton or a style; `ArmProbeMismatch`: a branch sample rendered another arm than the one it was derived for, an `@elmeragroup/intl` defect to report). An arm the branch pass does not reach is information, not a problem (see [Catalogs](#catalogs)). `--json` prints only `{ ok, problems: [{ code, message, fix, file?, line?, column?, locale?, key? }], messages, written, unreachable: [{ locale, key, arm, reason }] }` to stdout. Usage errors and unexpected failures (stack on stderr, prefixed `elmera-intl failed:`) exit 2. A style name (`{d, date, short}`, `{n, number, currency}`) that no configured style defines is not an error: next-intl, like the runtime, renders it as the kind's default format.

- `extract --watch` syncs the catalogs on every save (debounced), add-only: it never removes an entry or a translation, and on a parse error it prints the error and keeps the last catalogs. Run `extract` before committing so unused entries go (`check` fails on them).
- `extract --watch` follows an edit of `elmera-intl.json`: when the config's text changes, it prints `elmera-intl.json changed, restarting the watch` and restarts on the config as edited (a new locale, a changed `include` or `catalogs`). A config edited into an invalid one stops the watch and prints the problem, and the next edit that fixes it starts the watch again. It reads the config again every 250 ms, or every `--poll` interval, so any edit is followed: a save in place or an atomic replace, a repointed or restored symlink, a config created later. An edit made while the watch starts is followed once that start ends. A config invalid when the watch starts still fails it. Ctrl-C while the operating system holds the config's read (a hung network mount) stops the watch at once, and the process exits when that read returns; a second Ctrl-C ends it at once.
- `extract --watch` listens for the platform's file events. `--poll <ms>` (10 to 2147483647) walks the watched files instead, each time `<ms>` after the previous walk of them all, or the first sync, ends and never during that sync (a change is seen within one interval plus two walks of them all when the event loop is free, and its catalog updated once any running sync, the debounce and the sync are done), skipping `node_modules` and excluded directories and reporting one it cannot read, for a host whose events arrive late or not at all (a container's bind mount, a network drive, a macOS whose `fseventsd` is saturated); `vite dev` polls the same way whenever Vite's watcher was told to poll: by `CHOKIDAR_USEPOLLING` when it is set, otherwise by `server.watch.usePolling`, at the watcher's interval (`CHOKIDAR_INTERVAL`, otherwise `server.watch.interval`; one out of that range is reported, and the default 100 ms is used). A task runner that filters the environment, such as turbo in its strict mode, has to pass both variables through to `vite dev`.

## Catalogs

A PO file is read as GNU msgcat reads it: an entry starts at `msgctxt`, or at a `msgid` not after one, blank line or not; a comment belongs to the entry it precedes; every `#,` line is read; obsolete (`#~`) entries and comments after the last entry are dropped. Entries carry `msgctxt`, `msgid`, `msgstr` and `#.`, `#:` and `#,` comments; translator comments (`# `), `#|` and `msgid_plural` fail with the line. `extract` writes each value on one line. The reader and writer are this package's own (an Effect `Schema` codec), conformant with the PO library it replaced wherever GNU msgcat agrees (`test/po-conformance`, credited in NOTICE).

`compileCatalog(po, locale, { formats })` (`/compile`) is the one compiler; the loaders, `loadCatalog` and `check` all call it. It returns the catalog or a `CatalogCompileError` listing every problem:

- Keys are `hashKey(keyOf(source, context))`, seven base-36 characters; a collision fails.
- Each entry is the parsed ICU as a compact tuple IR (plural offsets, skeletons and named styles kept). Every entry is shipped through JSON, decoded and compared with the parse, then dry-formatted from the decoded form through the runtime's own formatter: every number, date and time node alone with each legal value type, then a value per plural and select arm (`=N` values skipped for a category, the intended arm confirmed by a probe). A throw fails the compile, and so does a probe that finds another arm rendered.
- An arm the branch pass does not reach is listed in `Compiled.unreachable` (and `check --json`'s `unreachable`) as `{ locale, key, arm, reason }`, `arm` with its enclosing arms (`n:one>n:other`), and never fails: the node pass formatted its nodes. `reason` is `category-absent` (the locale has no such plural category: Finnish `few`), `shadowed` (proven dead by its path: an enclosing selector on the same argument, as the inner `other` under an outer `one` of the same plural, which ICU requires, or exact `=N` keys), or `not-sampled` (the search found no value without proving none exists, such as English `one` behind `=1` and `=-1`).
- `en` compiles every msgid (any locale's PO: they share msgids). Another locale's catalog is complete: an untranslated entry is its English source, marked so it formats in `en`. An entry that renders as its own source is left out (the runtime's `isLiteralSource`), and the runtime renders a missing key's plain source as is.

The app imports a locale's PO, and the host compiles it:

```ts
const CATALOGS = {
  en: () => import("./intl/nb.po?source"),
  nb: () => import("./intl/nb.po"),
} as const;
```

Types: reference `@elmeragroup/intl-tools/po` once (`/// <reference types="@elmeragroup/intl-tools/po" />` in a `.d.ts`). Only the configured locales' POs compile; another `.po`, or a missing one, fails the build. Node scripts and tests without a bundler call `loadCatalog(path, locale?)` (`/compile`) and pass the catalog to the provider like any other.

## Hosts

The server picks the request locale's compiled catalog and hands it to `<IntlProvider>`. No source is transformed; on Next, one runtime module is aliased (below).

Vite (TanStack Start):

```ts
import { intl } from "@elmeragroup/intl-tools/vite";

plugins: [intl(), tanstackStart() /* ... */];
```

`intl()` compiles `*.po` imports. An import is a configured catalog at the path the config names or at its real path, so catalogs named through a link (or a config reached through one) compile where the bundler resolved them; a file the catalogs of several locales link to is the catalog of none. During `vite dev`, the in-process watch follows an edit to `elmera-intl.json` without a server restart, as `extract --watch` does: it restarts on the config as edited (a new locale, a changed `include` or `catalogs`), also one that was invalid or missing when the server started, and reads the config itself, so one inside the Vite root or outside it (`config`), or behind a symlink, repointed or not, is followed alike, whatever Vite's watcher reports. Every compiled PO import compiles again with it, and open tabs are told at the change and again once the new watch has written its first sync's result; a PO save is announced as Vite's watcher reports it, during a restart too; and every `Written` result (a sync of the watch that reports what it wrote) sends one notice, wherever its POs lie (outside the Vite root, as with a `config` above it, under `server.watch.ignored`, or with `server.watch: null`), so a new locale's PO that a first sync's retry writes after a PO save superseded that sync is announced too. A sync that writes some POs and then fails reports `Failed` and sends no `Written` notice, only the restart's own when it was a restart's first sync. A restart whose watch fails to start logs `WatchFailed`, and the next edit retries; the server finishes starting once the watch on the config as it is then has synced. A watch that fails for good once started (a logger that throws on a result and again on its `SyncFailed`, a watcher that fails to close as the watch restarts) ends `vite dev` with `elmera-intl: the catalog watch ended` and the failure as its cause; during the server's close it is logged instead. When the Vite config imports `elmera-intl.json`, an edit restarts the whole dev server instead (Vite's own restart for a dependency of its config), and the new server starts its own watch. `vite dev` runs `extract --watch` in-process and, on a PO save, invalidates the catalog's modules and sends open tabs an event; `vite build` runs `check` first, and `vite build --watch` rebuilds on a change to the config, a catalog, the formats module or a source the check read (one the build never imports included; never a file in an output directory, `build.outDir` or an output `dir` of `build.rolldownOptions` (`build.rollupOptions` on Vite 6 and 7) resolved as the bundler resolves it, which each build rewrites), so a repaired source clears a failed check; a source created after that check is not watched until another of those changes ([#64](https://github.com/elmeragroup/intl/issues/64)). The root route renders `createCatalogReload(import.meta.hot)`'s component (`@elmeragroup/intl/start`), created at module level, which turns the event into `router.invalidate()`. A Vitest config takes `intlCatalogs()` alone: the `*.po` compile without the watcher or the check. The catalog plugin keeps compiled catalogs out of Vitest's file-system module cache (`fsModuleCache`, on by default), which keys a module by its own bytes: a catalog also depends on `elmera-intl.json` and the formats module, so a cached one would outlive an edit of either, in a watch rerun and in the next run alike. A `*.po` import compiles again whenever Vite's transform misses instead; every other module keeps the cache.

Next (Turbopack): `export default withIntl(config, { dir: import.meta.dirname })` (`/next`) adds the `*.po` rule. It returns Next's phase function, which Next calls with the phase it loads the config in, so it goes outermost: a wrapper applied outside it would get a function, not a config (a config that is itself a phase function calls `withIntl`'s result inside it: `export default async (phase, context) => withIntl(await config(phase, context), options)(phase)`). In a phase that compiles through Turbopack (`next build` and `next typegen`, `next dev` and a dev custom server, `next analyze`), it reads the project and refuses one it cannot use: `elmera-intl.json` missing or invalid, catalogs outside the root, or a request module or alias as below. Every other phase compiles nothing (`next start`, a production custom server, `next info`): there `withIntl` reads nothing and returns the config as passed, so a pruned deployment needs no `elmera-intl.json` and no source, and catalogs that lay inside the root at build time may lie outside the root Next detects there. `dir` is the Next project directory, which `process.cwd()` is not under `next build <dir>`: `elmera-intl.json` (or `config`, relative to it), the installed `next` and Next's root detection all resolve from it. The rule is scoped to the configured catalogs' paths below Turbopack's root (`outputFileTracingRoot`, else `turbopack.root`, else Next's own root detection from `dir`; catalogs outside that root fail `withIntl`, naming the setting that decides it, and with catalogs in it, a locale linked out of it is left to Turbopack, which refuses that locale's import) and appended beside any other `*.po` rule (such as next-intl's, in an app still migrating). That path is the catalogs' real one, their directory resolved through its links, since Turbopack matches a rule against the module it resolved: a config spelled through a directory alias of the app, or catalogs reached through a link inside the root, match where they lie; catalogs written inside the root through a link out of it are left to Turbopack, which refuses such an import. A link at or below the locale's segment (`locales/nb -> translations/nb-NO`) is resolved per configured locale: a locale whose catalog lies elsewhere than the pattern says is matched at its real path as well, and catalogs written outside the root whose locales' directories link into it are accepted, imported at a path inside the root (Turbopack resolves no import through a path outside it). next.config is read once, so a locale added behind a link while `next dev` runs needs a restart of `next dev`; one added where the pattern says does not. What this does not do: a `..` that climbs through a link in the config's path is resolved from where the link is written, not from its target ([#75](https://github.com/elmeragroup/intl/issues/75)), and catalogs reached through a link whose target does not exist yet get the ordinary root refusal. Every catalog import depends on `elmera-intl.json`, and every configured catalog's on its formats module, and Turbopack loads no dependency outside its roots: the root and `experimental.turbopackAdditionalRoots`. Where Turbopack compiles an import, the loader registers neither file when it lies outside them and fails the import with what is outside which root, and the fix: widen the deciding setting, or list a directory that holds the file, and neither holds nor lies in the root, as an additional root. The roots are those of the config `withIntl` is given, so a wrapper applied outside it that adds additional roots is not seen; keep `withIntl` outermost. A path counts as inside when it lies in a root as written, or a directory above it resolves through its links into one; the file itself is not resolved, as Turbopack does not. With an adapter selected (`adapterPath`, `experimental.adapterPath` or `NEXT_ADAPTER_PATH`), whose `modifyConfig` may add roots after next.config is evaluated, the loader checks nothing and Turbopack's own error stands. A PO save recompiles its module, and Next refreshes open tabs.

`withIntl` also adds a `turbopack.resolveAlias` entry from the runtime's request module (`@elmeragroup/intl/internal/request-module`) to the app's, whose default export is `createRequestConfig(adapter)` from `@elmeragroup/intl/next/server`; so no page, layout, server action or route handler imports setup code. `getIntl`, `getT`, `getFormat` and the server `<T>`/`useT` read `@elmeragroup/intl/internal/request-config`, whose `react-server` condition (server components, server actions and route handlers) alone imports the request module; client and SSR code resolve it to the runtime's stub, so a Client Component that imports `/server` by mistake gets the stub's error, naming that cause, and never bundles the adapter. The module is `./intl/request.ts`, aliased only when that file exists when next.config loads (restart `next dev` after creating it; an app that uses `withIntl` for its catalogs alone gets no alias), or the `request` option, relative to `dir`, always aliased. The target is a plain path relative to `dir`, merged with the app's own aliases. `withIntl` fails when `request` names `dir` itself or a directory above it, or when a `resolveAlias` key already maps the request module, exactly or as a wildcard whose pattern matches it (`@elmeragroup/intl/internal/request-mod*`; set the `request` option instead). Both fail only in a phase that compiles. Whether Turbopack can load the target is left to Next, which knows its layout (a pruned `next start` deployment without the source, symlinks, `experimental.turbopackAdditionalRoots`). Without the alias, when its target does not resolve, or when the request module lies outside Turbopack's root (Turbopack then falls back without an error), the runtime's request config rejects on first use, naming the fix. One cause the alias cannot see on Node server paths: listing `@elmeragroup/intl`, or a pattern that matches it, in `serverExternalPackages` makes Node load the runtime unbundled, past the alias, so every request there reads the stub; leave the runtime out of that list. An Edge route still bundles the runtime and keeps the alias.

Check and the watcher run as scripts, because Next loads its config in more than one process:

```json
{
  "dev": "concurrently \"next dev\" \"elmera-intl extract --watch\"",
  "build": "elmera-intl check && next build"
}
```

## Vitest

`globalSetup: ["@elmeragroup/intl-tools/vitest"]` runs `check` in the vitest project root and fails the run on any problem it finds. The installed package ships built; where a workspace links it from source instead, build it first (turbo `^build`), or vitest stops with "Failed to load url @elmeragroup/intl-tools/vitest".

## Lint

```json
{
  "jsPlugins": [{ "name": "elmera-intl", "specifier": "@elmeragroup/intl-tools/oxlint" }],
  "rules": { "elmera-intl/extractable": "error" }
}
```

The rule runs the extractor itself on every script file, with no text pre-filter, so lint and `extract` agree on every file.
