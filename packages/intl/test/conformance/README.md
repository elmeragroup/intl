# next-intl conformance suite

next-intl's own message-formatting and formatter tests, ported from tag `v4.14.9` (the version the first adopting app ran) and run against our public API: `createIntl` + `t`, `<T>` under `<IntlProvider>` for rich text, and `intl.format` / `useFormat()` for the formatter. The oracle is next-intl's hand-written expected output, copied verbatim. Every message goes through `compileCatalog` (intl-tools) first, as an app's catalog does: `strict.tsx` compiles each `t` message, and each `<T>` a first render reports as not extracted, then formats from the compiled catalog. It also makes `onError` throw, so a message missing from the catalog or one that fails to format cannot pass.

The ported cases and their expected outputs are next-intl's, used under its MIT license: see [LICENSE-next-intl](LICENSE-next-intl).

Every case in the source files is counted once below: ported (asserts next-intl's output and passes), deliberate difference (asserts ours and names next-intl's), or excluded. An `it.each` counts as one case per row in `createTranslator.test.tsx`'s skeleton table (44 rows) and `createFormatter.test.tsx`'s numeric-representation table (48 rows); "applies a time zone when using a built-in format" counts as one case, though it holds 8 expectations (ported as 8 rows).

## Ported with an adaptation

- Per-call formats (`t(key, values, formats)`) are not part of our API. The 9 cases that pass them configure the formats next-intl merges for that call (global, then the call's) on the instance, and assert the same output.
- next-intl's suite runs with `TZ=Europe/Berlin` and often no configured zone; ours always configures one, so those cases pass `Europe/Berlin` (or the zone next-intl's provider sets).
- Rich text: next-intl writes `<b>Hello {param}</b>` with tag renderers; `<T>` writes the same message as JSX, and the rendered HTML is compared.
- The Latvian plural case formats an lv translation of an English source, since our messages are keyed by their English source.
- Formatter error handling (7 cases: useFormatter's 6, createFormatter's dateTimeRange fallback): next-intl reports an `IntlError` with a code (`MISSING_FORMAT`, `FORMATTING_ERROR`); ours reports a tagged error (`FormatNotFound`, `FormatFailed`, whose message carries `Intl`'s verbatim). The rendered fallback is next-intl's, asserted as next-intl asserts it.
- Formatter dates next-intl builds in host-local time (`new Date(2007, 0, 10, 10)`, read as Berlin under its `TZ=Europe/Berlin`) are the same Berlin instants (`2007-01-10T10:00:00+01:00`); this suite runs under America/Los_Angeles.
- `createFormatter.test.tsx` was recorded on an ICU that put U+202F before AM/PM (3 strings, 6 occurrences); Node's ICU 78, and use-intl 4.14.9 itself run on it, prints a space there, so those strings have a space. `useFormatter.test.tsx` already has the space.
- next-intl's `relativeTime` and `useFormatter` cases render through `@testing-library/react` and parse dates with `date-fns`; ours renders `useFormat()` with `renderToStaticMarkup` and parses with `new Date`. The relative-time unit cases are one `it.each` with next-intl's names.
- useExtracted's object form and descriptions: `id` and `description` do not change the output, and ours keys by source, so those cases assert the output of the message alone.
